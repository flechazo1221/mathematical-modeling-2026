# 基准、改进与验证合同

本参考用于把“不要迷信复杂算法”落实为 H2 可审查的设计证据。重点是改进是否解决真实问题，而不是模型是否新颖。

## 每个子问题的最低设计单元

至少给出一个能回答同一问题的简单可信基准。可按任务选取：

| 任务 | 常用基准 | 只有诊断支持时才考虑的方向 |
| --- | --- | --- |
| 预测 | 上一期值、均值、线性回归 | 周期、外生变量、非线性 |
| 分类 | 多数类、Logistic | 类别权重、阈值、树模型、特征工程 |
| 排序 | 等权评分 | 客观或组合赋权、稳健排序 |
| 优化 | 现行方案、简单规则或贪心 | 完整约束、全局求解、多目标或稳健优化 |
| 仿真 | 稳态或简化模型 | 动态参数、随机性、空间结构 |

基准与改进必须回答相同决策问题。比较时固定数据、训练测试划分、指标、约束和计算口径；若模型性质迫使某项不同，预先说明原因、影响和补偿性检验。

## 复杂度准入

仅当下列条件得到满足或能在原型阶段直接验证时，才把复杂方案列为可保留候选：

- 基准留下可描述的非线性、周期、交互、约束违反、偏置或高代价错误；
- 样本量、变量质量和识别条件足以支撑新增自由度；
- 预期提升能由样本外指标或等价的独立证据验证；
- 增加复杂度后仍能解释、复现并在时间与算力预算内完成参数和稳定性检查。

不得仅凭“随机森林换成 XGBoost”等模型替换宣称改进。每个改进使用下表记录：

| 字段 | 要求 |
| --- | --- |
| 基准及表现 | 基准定义、指标、失败案例或待验证现象 |
| 诊断出的不足 | 指向具体机制、残差结构、约束或错误代价 |
| 已进行/拟进行的优化 | 数据处理、假设、模型结构、约束、求解或验证变化 |
| 优化方向 | 下一步可检验的改进，不写空泛的“继续调参” |
| 预期证据 | 指标、图表、约束检查或情景结果 |
| 保留门槛 | 有实际意义的最小提升及稳定性要求 |
| 回退条件 | 未达门槛时回到基准、删去模块或重新诊断 |

## 验证分工

- 灵敏度分析回答“哪个参数最影响结果”，优先覆盖关键参数及合理区间；记录结果变化范围、核心结构是否改变和最需要准确估计的参数。
- 鲁棒性分析回答“数据或环境变化后还能否使用”；可比较乐观、正常、悲观情景下的目标值、约束风险、方案结构和最差表现。
- 消融分析回答“哪个模块真正带来提升”；逐个移除特征、周期项、外部变量、校正或约束模块，并报告相对完整模型的变化。

验证计划按问题风险选择强度，不机械堆齐三类分析。灵敏度为默认重点；存在环境漂移或参数不确定时强化鲁棒性；声称某模块是创新时必须安排消融。结果不得预写为“稳定”或“显著”，应预先定义判断阈值。

## H2 优化审计与方向

`H2-优化审计与方向.md` 必须面向队员而不是面向算法清单，逐个子问题列出：

1. 已建立的基准及其作用；
2. 相比基准已经设计并进入原型验证的优化；
3. 每项优化解决的具体不足和证据状态：已验证、待验证或证据不足；
4. 尚可尝试的优化方向、触发条件、成本和预期收益；
5. 灵敏度、鲁棒性、消融和其他验证的优先级；
6. 建议保留、暂缓或回退的模块及理由。

“已进行的优化”只能指已有设计变更或已有原型证据；尚未实施的内容必须标为“优化方向”，不得混写。该文件不替团队选择最终路线。
